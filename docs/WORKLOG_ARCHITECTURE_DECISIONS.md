# Worklog Architecture Decisions

**Status**: Fase 1 (Fundação) — em desenvolvimento, 2026-07-17
**Escopo**: decisões arquiteturais do módulo Worklog (`src/modules/worklog/`), a solução nativa de controle de horas do ArchFlow. Segue o formato e a numeração globais definidos em `ARCHITECTURE_GOVERNANCE.md` §1 — cada ADR abaixo é obrigatória antes do código correspondente. Numeração continua de `CORE_ARCHITECTURE_DECISIONS.md` (a mais recente é ADR-020, Entity Lifecycle) — esta ADR usa 021-023.

Worklog é o segundo módulo de produto construído sobre a fundação congelada do Financeiro/Compras, e o primeiro a introduzir estado *ao vivo* (um cronômetro em execução, visível globalmente, persistente entre navegação/refresh) — uma classe de requisito que nenhum módulo anterior teve. Reaproveita três padrões já hardenados (CAS de transição de estado do Compras, Entity Lifecycle do Core, `PERMISSIONS`/RBAC do Financeiro) e resolve um problema novo (concorrência "um cronômetro ativo por usuário" sem lock distribuído).

## ADR-021 — Um cronômetro ativo por usuário via índice único esparso, em vez de lock

**Problema**: o produto exige que cada usuário tenha **no máximo um** `TimeEntry` com status `RUNNING`/`PAUSED` a qualquer momento — mesma regra que motivou o Timer Global do frontend ("Você já possui um cronômetro em execução. Deseja finalizá-lo e iniciar um novo?"). Sem essa garantia no banco, dois cliques quase simultâneos (duas abas, retry de rede, o widget global e a tela Worklog abertos ao mesmo tempo) podem criar dois `TimeEntry` `RUNNING` para o mesmo usuário — um "cronômetro fantasma" que o widget nunca mais encontra.

**Alternativas consideradas**:
- Checagem de leitura-antes-de-escrever dentro da transação (`findFirst({ status: {in: [RUNNING,PAUSED]}, userId })` seguido de `create` se vazio) — rejeitada: sem uma constraint do banco por trás, duas transações concorrentes podem ambas passar pela leitura antes que qualquer uma escreva (MongoDB não tem `SELECT ... FOR UPDATE`); a garantia dependeria inteiramente do `withTransactionRetry` acertar a corrida por sorte de timing, não por construção.
- Lock distribuído (ex.: documento de lock próprio, mesmo padrão que um Redis lock faria) — rejeitada: introduziria uma peça de infraestrutura nova (nenhum lock distribuído existe hoje no codebase) para resolver um problema que o próprio schema já pode expressar como constraint.
- **Índice único esparso via campo auxiliar** (`activeOwnerId`) — a escolhida, **com uma correção importante em relação à primeira versão deste ADR**: `Prisma`'s `@unique` no MongoDB **não é sparse** (`docs/indexes.md` — confirmado, não de memória: MongoDB trata `null` como um valor igual a qualquer outro `null` num índice único gerenciado pelo Prisma, então dois `TimeEntry` com `activeOwnerId: null` — ou seja, qualquer par de entradas `COMPLETED`/arquivadas — colidiriam entre si sob um `@unique` do schema). Este é exatamente o mesmo bug que `PurchaseOrder.financialDocumentId` sofreu na Fase 1 de Compras, pego de verdade por `scripts/rc-compras-approve-check.ts` e documentado em `docs/indexes.md` ("Compras — purchase_orders.financialDocumentId Sparse Unique Index") — a correção aqui reaproveita a mesma resposta, aplicada antes do código em vez de descoberta depois por um script de concorrência.

**Solução escolhida**: `TimeEntry.activeOwnerId String? @db.ObjectId` no `schema.prisma`, **sem** `@unique` do Prisma. A constraint real é um **índice único esparso criado manualmente** no MongoDB (`{ activeOwnerId: 1 }`, `unique: true, sparse: true`), registrado em `docs/indexes.md` — nova seção "Worklog — time_entries.activeOwnerId Sparse Unique Index", mesmo formato/processo da entrada de Compras, necessário em todo ambiente (local/staging/produção) antes do primeiro `start()` real. `start()` executa `create({ ..., activeOwnerId: userId, status: "RUNNING" })` dentro de `withTransactionRetry`; se o Mongo retornar violação de índice único nesse campo (mapeado pelo Prisma como `P2002`, mesmo comportamento de um índice único do schema), o repository trata como conflito esperado — não relança o erro cru, re-busca a entrada ativa existente do usuário (`findFirst({ workspaceId, userId, status: { in: ["RUNNING","PAUSED"] } })`, nunca por `activeOwnerId` sozinho — esse campo não tem índice de leitura próprio, só a constraint de escrita) e retorna um erro de domínio `TIMER_ALREADY_RUNNING` carregando essa entrada, para o frontend oferecer "finalizar e iniciar um novo" (mesmo espírito de recuperação de `P2002` que `purchaseOrder.repository.ts#create` já usa para `idempotencyKey`, aplicado a um propósito diferente — lá é replay da mesma intenção, aqui é rejeição de uma segunda intenção concorrente). `pause()`/`resume()` mantêm `activeOwnerId` preenchido (o timer continua "ativo" enquanto pausado — só não está contando). `stop()` limpa `activeOwnerId` para `null` na mesma transação que seta `status: "COMPLETED"` e calcula `durationSeconds`, sempre via CAS (`updateMany({ where: { id, workspaceId, userId, status: { in: ["RUNNING","PAUSED"] } } })`) — mesmo padrão de `approve()`/`cancel()` do Compras (ADR-017), reaplicado a três transições em vez de uma.

**Correção de schema durante a implementação**: a primeira versão deste ADR usava apenas `startedAt`/`pausedAccumSec` para calcular a duração, o que exigiria sobrescrever `startedAt` a cada `resume()` — perdendo o horário original de início para exibição/relatório. Corrigido antes do primeiro uso real: `TimeEntry` ganhou `lastResumedAt DateTime?`, que marca o início do span `RUNNING` atual e é resetado a cada `resume()`; `startedAt` permanece imutável desde a criação. `pause()`/`stop()` sempre calculam o span corrente como `now - lastResumedAt`, somado a `pausedAccumSec` (que acumula os spans já fechados).

**Risco residual documentado**: até o índice manual ser criado no ambiente (passo de deploy, não automático via `db:push` — mesma limitação que já vale para `supabaseId` e `financialDocumentId`), a invariante "um timer ativo por usuário" **não** está protegida por constraint de banco, só pela leitura-antes-de-escrever dentro da transação — mesma janela de corrida rejeitada como solução única mais acima. O item 12 do checklist (script de concorrência real) deve rodar depois do índice manual criado localmente, para validar a proteção de fato, não a ausência de erro por sorte de timing.

**Justificativa**: a pergunta do `MODULE_CREATION_CHECKLIST.md` Q1 ("se duas operações independentes podem competir em torno do mesmo aggregate, qual é o mecanismo de serialização?") tem aqui uma resposta diferente da do Financeiro/Compras porque o conflito não é "duas operações no mesmo documento" (isso já é resolvido por CAS convencional em `pause/resume/stop`) — é "duas operações tentando criar documentos *diferentes* que juntos violariam uma invariante do usuário". Um índice único esparso é a ferramenta correta para esse formato específico de invariante (existe *no máximo um* de algo, não "este documento específico está num estado válido") — usar CAS aqui exigiria inventar um documento "singleton por usuário" só para ter algo a fazer CAS contra, complexidade desnecessária quando o próprio MongoDB já resolve isso nativamente.

**Impacto futuro**: qualquer invariante futura da forma "no máximo um X ativo por Y" (ex.: um futuro "aprovação de timesheet em andamento por usuário", banco de horas) pode reaproveitar a mesma técnica — campo auxiliar `@unique`, preenchido só durante o estado exclusivo, limpo fora dele — em vez de reinventar um mecanismo de lock a cada novo caso.

## ADR-022 — RBAC com visibilidade restrita (tier Financeiro), própria entrada sempre liberada

**Problema**: `TimeEntry.isBillable`/duração agregada por colaborador é informação sensível do ponto de vista financeiro (hora faturável vira faturamento, o mesmo raciocínio que já tornou Financeiro e Compras não-`read:*` — ADR-007/018) — mas, diferente de Financeiro/Compras, **todo usuário precisa poder registrar seu próprio tempo independente do papel**, porque é o próprio trabalho da pessoa sendo rastreado, não uma operação administrativa sobre terceiros. Uma DESIGNER que não pode ver o Financeiro do escritório ainda precisa iniciar seu próprio cronômetro.

**Alternativas consideradas**:
- Aplicar o mesmo tier do Financeiro sem exceção (DESIGNER sem nenhuma permissão de `time-entries`) — rejeitada: bloquearia a própria DESIGNER de registrar o próprio tempo, o oposto do objetivo do módulo (o prompt original lista "Timer" como funcionalidade universal, não administrativa).
- `read:*` universal para tudo em Worklog (nenhuma restrição, como a maioria dos módulos de produto que não são Financeiro/Compras) — rejeitada: exporia a visão de equipe/dashboard agregado (Fase 2 — "quem está trabalhando, quanto tempo, em qual projeto") e horas faturáveis a qualquer papel, mesma exposição de margem que motivou a exceção do Financeiro.
- **Duas granularidades separadas** — a escolhida: permissões amplas para a própria entrada (mesmo tier de `update:tasks`, concedido a todos exceto `VIEWER`), permissão restrita e explícita (`view:time-entries`) só para consultar entradas de **outros** usuários.

**Solução escolhida**: nova família de permissões:
- `create:time-entries`, `update:time-entries` — concedidas a `ADMIN`, `ARCHITECT`, `DESIGNER`, `ASSISTANT` (todos exceto `VIEWER`), mesmo tier de `update:tasks` (`rbac.ts:52,78,99,119`) — cobre iniciar/pausar/retomar/finalizar/editar/lançar manualmente **a própria** entrada. Toda rota que modifica um `TimeEntry` reforça no service que `entry.userId === user.sub` **exceto** quando o chamador também tem `view:time-entries` (permite a um ADMIN corrigir o lançamento de outro usuário, mesmo padrão de "quem pode ver tudo também pode administrar tudo" implícito no tier Financeiro).
- `delete:time-entries` (arquivar a própria entrada) — mesmo grupo (`ADMIN`/`ARCHITECT`/`DESIGNER`/`ASSISTANT`), já que arquivar é sempre reversível (ADR-020) e é a própria entrada da pessoa.
- `view:time-entries` — visibilidade de entradas de **terceiros** (base da visão de equipe/dashboard agregado da Fase 2) — só `OWNER`, `ADMIN`, `ARCHITECT`, mesmo tier de `view:financial-dashboard` (`rbac.ts:60,86` — nota: `ASSISTANT` tem `view:financial-documents` mas não `view:financial-dashboard`; aqui `ASSISTANT` fica de fora de `view:time-entries` inteiramente, porque não há um "ver documento individual de outro colaborador" sem ser visão agregada de equipe no Worklog, ao contrário do Financeiro que separa documento individual de dashboard).
- `manage:worklog-settings` (CRUD de `ActivityCategory`) — mesmo tier de `manage:financial-settings` (`rbac.ts:61`), só `OWNER`/`ADMIN`.
- `VIEWER` — nenhuma permissão de Worklog (não registra tempo, não vê tempo de terceiros), mesmo tratamento que já recebe em todo o resto do app.

**Justificativa**: o precedente do Financeiro/Compras resolve "quem pode ver/administrar dados de terceiros" mas não tinha precedente para "toda pessoa administra seus próprios registros, mas não os de terceiros, sem que isso seja uma exceção de ownership como `requirePermissionOrOwner`" (que é para uma exceção pontual — DESIGNER editando um Project que criou —, não o modo de operação padrão de um módulo inteiro). Separar "ação sobre o próprio recurso" (permissão ampla) de "ação sobre recurso de terceiros" (permissão restrita) como duas famílias de permissão, em vez de uma checagem de ownership por cima de uma permissão única, deixa a intenção explícita no mapa `PERMISSIONS` em vez de escondida numa condicional de service.

**Impacto futuro**: qualquer módulo futuro com a mesma forma ("todo usuário administra o próprio X, só alguns papéis veem o X de terceiros") — ex.: banco de horas, avaliações de desempenho — segue este padrão de duas famílias de permissão em vez de reaproveitar `requirePermissionOrOwner` (reservado para exceções pontuais, não para o modo de operação padrão do módulo).

## ADR-023 — Worklog não entra na lista Core nesta fase, mesmo sendo um módulo estratégico

**Problema**: o pedido de produto trata Worklog como "um dos módulos mais estratégicos do ArchFlow" e pede que seja tratado como módulo Core. `CORE_MODULE_POLICY.md`, porém, define "Core" com um significado técnico específico e restrito — não "importante para o produto", mas "mudança estrutural exige ADR obrigatória" — e sua própria lista já documenta que **Compras**, um módulo de produto major recém-lançado, foi deliberadamente deixado de fora ("Compras após estabilizar") e que Billing é "não-Core nesta versão... vira candidato quando a dívida técnica for resolvida via ADR própria". Aplicar "Core" ao Worklog no dia 1 da Fase 1 — antes de qualquer ciclo de produção, RC ou histórico de incidente — contradiz o próprio precedente que a política estabelece para módulos de produto novos.

**Alternativas consideradas**:
- Adicionar Worklog à tabela "Módulos Core" de `CORE_MODULE_POLICY.md` agora, atendendo ao pedido literal — rejeitada: a própria política diz que "adicionar um módulo à lista Core... é, ele próprio, uma ADR" com critério de estabilização, não de importância de produto declarada antecipadamente; forçar isso agora criaria uma segunda vara de medir (Compras estabiliza para entrar, Worklog entra de graça) sem justificativa registrada.
- Ignorar o pedido de "módulo Core" e tratar Worklog como módulo de produto comum, sem qualquer nota — rejeitada: perderia a intenção de produto real por trás do pedido (Worklog não é uma feature descartável, é uma aposta estratégica de longo prazo do produto) e não deixaria rastro de que a divergência entre "Core de produto" e "Core de governança técnica" foi percebida e não apenas esquecida.
- **Registrar a distinção explicitamente e tratar "Core" como intenção de produto, não como entrada na allow-list técnica desta fase** — a escolhida.

**Solução escolhida**: Worklog **não é adicionado** à tabela de Módulos Core em `CORE_MODULE_POLICY.md` nesta fase. Em vez disso:
- Worklog **consome** módulos Core existentes como qualquer módulo de produto tem permissão de fazer: `RBAC` (nova família de permissões, ADR-022), `Entity Lifecycle` (delegação total de archive/restore, nunca reimplementado — ver `entityLifecycle.service.ts`), `Logging`/`Retry` (auditoria e `withTransactionRetry` em toda escrita transacional). Nenhuma dependência proibida pela política é violada.
- A intenção de produto ("módulo estratégico, tratado como Core do ponto de vista de prioridade e investimento de longo prazo") fica registrada aqui e no `DOMAIN_GUIDE.md` (bounded context "Worklog", ver atualização abaixo) — mas a promoção formal à lista técnica Core fica condicionada ao mesmo critério que Compras: estabilização em produção (volume real, pelo menos um ciclo sem RC crítico) mais uma ADR própria no momento, seguindo `CORE_MODULE_POLICY.md`'s regra final ("adicionar um módulo à lista Core é, ele próprio, uma ADR").
- Worklog é registrado no `DOMAIN_GUIDE.md` §1 (tabela de Bounded Contexts) como um contexto de produto novo, com módulo de código `src/modules/worklog/`, mesma linha de tratamento que Compras recebeu.

**Justificativa**: seguir a definição técnica documentada da própria política, em vez de reinterpretar "Core" ad-hoc para este pedido, preserva o valor da lista Core como um sinal confiável ("estes módulos exigem ADR para qualquer mudança estrutural") — se qualquer módulo que o produto considerasse importante entrasse na lista sem o mesmo crivo de estabilização, a lista deixaria de discriminar "infraestrutura testada por incidentes reais" de "prioridade de roadmap", que são perguntas diferentes.

**Impacto futuro**: quando Worklog tiver volume de produção real e passar por pelo menos um ciclo de estabilização (mesmo gatilho que Compras aguarda), a promoção a Core é uma ADR nova, curta, que só precisa apontar para o histórico de estabilidade acumulado — não uma reabertura desta decisão.
